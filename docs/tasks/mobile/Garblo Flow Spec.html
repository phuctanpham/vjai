Garblo Flow Spec

Four flows, written up as a build spec. The MUST-HAVE MVP: Flow A turns photos into structured wardrobe items, and Flow B styles outfits from those items only. Version 2 adds the NICE-TO-HAVE flows behind feature flags: Flow C rewards rewearing, and Flow D lets people share their progress with the community.

Each use case has a user story, acceptance criteria, a user flow, a data flow and a sequence diagram. Parts marked EXTRA go beyond what the screens show (empty, loading and error states, data erasure, API contracts). Use the switches in the index to hide extras, or to read only the must-have spec.

V1 Nice-to-have scope NICE-TO-HAVE

Version 2 adds six nice-to-have features, each behind a feature flag. They only read data the must-have flows already produce: wear logs, liked looks and dormancy. They never block a must-have path, and if one fails, the app falls back to its v1 behaviour.

T2 Canonical data model

One schema behind both flows

Logical model (v2.4). The tables and ERDs below describe entities and rules. The physical design is MongoDB collections synced to SQLite by PowerSync (T4). Postgres constructs such as triggers and CHECK constraints are implemented as backend validators, $jsonSchema rules and derived queries.

The eight screens add up to 16 tables in 4 groups: Studio ingestion (batch → photo → AI job → draft item), Wardrobe (items, taxonomy, wear log), Gu Match (session → context → candidates → interactions, try-on) and Privacy (consents). wardrobe_items is the shared table. Flow A writes it; Flow B reads it, and only for the signed-in user.

Decisions applied

IDDecisionEffect on the model
C2Any photo yields 0..n itemsEach extracted_items and wardrobe_items row keeps its own source_asset_id. The 4a banner is computed per batch: "From {photos} photos, AI found {items} items".
C4Two-level taxonomyThe item_groups enum (TOPS, BOTTOMS, SHOES, BAGS, HATS, and ACCESSORIES since v2.1, P6) drives the 5a chips. The item_types lookup (Shirt, T-shirt, Wide-leg trousers, Sneakers…) is what the 4a Type field edits, and each type belongs to one group. The 4a item is named by its type ("Violet shirt").
C6One job per photo × taskai_jobs is unique on (batch, photo, task). Pose and background jobs end as SKIPPED_NO_PERSON when the photo has no person.
C3Ask "Last worn" during review4a gets an optional last_worn_input on extracted_items. Save copies it to wardrobe_items.last_worn_at with last_worn_estimated = true.
C10Occasion chips are multi-selectgu_match_sessions.occasions is an array of 0–5 values
C1Two context pathsgu_match_sessions.path is PROMPT_LED or ZERO_INPUT. Snapshot event fields are nullable. Weather records its own location, separate from the header's current location.
C7Progressive revealNo schema change. Snapshot cards stream as SSE events before the snapshot row is complete.
D1Spec decision: draft items before saveThe sources insert into wardrobe_items only when 4a's save runs, but the AI results must be stored somewhere before that. They live in extracted_items, which is editable and confirmed by the user. Save copies them over in one transaction.
D2Spec decision: batch state AWAITING_REVIEWAdded between AI_PROCESSING and COMPLETED, so a batch reads "ready for 4a" and stays resumable if the user leaves before saving.
D3Spec decision: one consent record per user and versionConsent is reused across batches and try-on, not inserted again on every submit. Each batch points at the consent that was active when it was submitted.

T2+ Data model · v2 NICE-TO-HAVE

Impact is computed, rewards are a ledger, Community is members-only

Every Impact number is derived from wear events, wardrobe items and check-ins. The source stored them as columns with demo defaults, which this spec drops (F1). XP is a ledger of idempotent entries, so replays and retries can't double-count. Share and Community are a separate group of tables, members-only and opt-in.

N3Worn combinations + item coverageA new wear_events table groups one day's outfit. Its signature (a hash of the sorted item IDs) identifies a combination. A "new look" is a signature first worn in the current month. Rewear rate = items worn in the last 30 days ÷ non-archived items.
N4Monthly self-reportpurchase_checkins (one per user per month) and baseline_monthly_purchases from onboarding. The tile is hidden until 2 check-ins exist and is labelled "self-reported".

T4 Offline-first data platform · SQLite + PowerSync + MongoDB

SQLite on the phone, PowerSync in the middle, one MongoDB replica set for the pilot

The Flutter app reads and writes a local SQLite database managed by the PowerSync SDK. PowerSync streams each user's data down from MongoDB through change streams. // lib/data/connector.dart  (illustrative)
class GarbloConnector extends PowerSyncBackendConnector {
  @override
  Future<PowerSyncCredentials?> fetchCredentials() async {
    final t = await auth.currentToken();            // anonymous or Google-linked, same sub
    return PowerSyncCredentials(endpoint: env.powerSyncUrl, token: t.jwt);
  }

  @override
  Future<void> uploadData(PowerSyncDatabase db) async {
    final tx = await db.getNextCrudTransaction();
    if (tx == null) return;
    final res = await api.applyTransaction(tx);    // POST /v1/sync/tx {tx_id, ops[]}
    if (res.applied || res.permanentlyRejected) {
      await tx.complete();                          // never block the queue on a 4xx
    } else {
      throw RetryableUploadError(res);              // 5xx/network: the SDK retries
    }
  }
}
